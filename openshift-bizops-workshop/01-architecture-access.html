OpenShift BizOps Operations Workshop

Map the path from Pod to Service to Route, confirm the application is reachable from outside the cluster, and practice reading deployment and health status. This session builds on the baseline app from Cluster Setup.

Prerequisites

  • Baseline application deployed from Cluster Setup

  • oc authenticated with context cluster

  • Working directory is the workshop repository root

This session is mostly inspection. You will not replace the demo app yet.

How It Works

OpenShift exposes HTTP applications with this common path:

  1. Pods run containers and listen on a container port (8080 for this demo).

  2. A Service selects pods by label and provides a stable ClusterIP.

  3. A Route points at the Service so the cluster ingress (router) can admit external traffic.

Understanding that chain is the foundation for every later operations task.

Steps to Apply

1. Map Pod to Service to Route

What: List the core objects and confirm labels and selectors line up.

Why: Most "app is down" tickets start with a broken link in this chain (wrong selector, no endpoints, Route not admitted).

oc get pods,svc,route -n bizops-demo -o wide --context cluster
oc get endpointslice -n bizops-demo -l kubernetes.io/service-name=demo-app --context cluster
Verify: EndpointSlice lists Ready pod IPs on port 8080 
oc describe svc demo-app -n bizops-demo --context cluster | sed -n '1,25p'
oc get endpointslice -n bizops-demo -l kubernetes.io/service-name=demo-app -o wide --context cluster
Name:              demo-app
Namespace:         bizops-demo
Selector:          app=demo-app
Type:              ClusterIP
IP:                172.30.x.x
Port:              http  8080/TCP

NAME             ADDRESSTYPE   PORTS   ENDPOINTS                   AGE
demo-app-xxxxx   IPv4          8080    10.128.x.x,10.129.x.x       5m
On OpenShift 4.19+ / Kubernetes 1.33+, prefer EndpointSlice over the legacy Endpoints API.

2. Verify external application access

What: Resolve the Route hostname and request the application over HTTP.

Why: BizOps must confirm users can reach the app from outside the cluster, not only that pods are Running.

export ROUTE_HOST=$(oc get route demo-app -n bizops-demo -o jsonpath='{.spec.host}' --context cluster)
echo "https://${ROUTE_HOST}"
curl -sI "http://${ROUTE_HOST}" | head -n 5
Some clusters terminate TLS on the router and redirect HTTP to HTTPS. If curl follows redirects or fails TLS verification against a workshop CA, use curl -skI with the HTTPS Route URL and prefer trusting the cluster CA in production.
Verify: HTTP response is successful (2xx or expected redirect) 
curl -s -o /dev/null -w "%{http_code}\n" "http://${ROUTE_HOST}"
200

3. Review deployment status

What: Inspect the Deployment, ReplicaSet, and rollout history.

Why: Deployment status tells you whether the desired replica count and image revision are actually live.

oc get deploy,rs -n bizops-demo --context cluster
oc rollout status deployment/demo-app -n bizops-demo --context cluster
oc rollout history deployment/demo-app -n bizops-demo --context cluster
Verify: Desired and available replicas match 
oc get deployment demo-app -n bizops-demo -o wide --context cluster
NAME       READY   UP-TO-DATE   AVAILABLE   AGE   CONTAINERS   IMAGES
demo-app   2/2     2            2           10m   httpd        registry.access.redhat.com/ubi9/httpd-24:latest

4. Monitor pod, application, and service health

What: Check Ready conditions, recent events, and probe configuration.

Why: Running is not the same as Ready. Probes and events explain why traffic may be failing even when pods exist.

oc get pods -n bizops-demo --context cluster
oc get events -n bizops-demo --sort-by='.lastTimestamp' --context cluster | tail -n 20
oc get pod -n bizops-demo -l app=demo-app -o jsonpath='\{range .items[*]}\{.metadata.name}\{" ready="}\{.status.conditions[?(@.type=="Ready")].status}\{"\n"}{end}' --context cluster
Verify: Both demo-app pods report Ready=True 
oc get pods -n bizops-demo -l app=demo-app --context cluster
NAME                        READY   STATUS    RESTARTS   AGE
demo-app-6d8f7c9b4d-abc12   1/1     Running   0          10m
demo-app-6d8f7c9b4d-def34   1/1     Running   0          10m

5. Inspect light traffic routing

What: Read Route weight and Service port mapping that steer traffic to the demo app.

Why: BizOps often adjusts Route weights or Service target ports when shifting traffic between backends; start by reading the current path.

oc get route demo-app -n bizops-demo -o yaml --context cluster | sed -n '/^spec:/,/^status:/p'
oc get svc demo-app -n bizops-demo -o yaml --context cluster | sed -n '/^spec:/,/^status:/p'
Verify: Route targets Service demo-app with weight 100 and port http 
oc get route demo-app -n bizops-demo -o jsonpath='service={.spec.to.name} weight={.spec.to.weight} port={.spec.port.targetPort}{"\n"}' --context cluster
service=demo-app weight=100 port=http

Alternatives Considered

Approach Notes

OpenShift Route + Service

Fits empty OCP clusters and this workshop without extra operators

Kubernetes Ingress only

Valid on some platforms; Route is the native OpenShift path used here

Service mesh traffic shifting

Powerful but out of scope for a one-hour BizOps intro

Reset

This session only inspected resources. No reset is required. If the baseline app was changed accidentally, re-apply setup manifests:

oc apply -f 00-baseline/ --context cluster
oc rollout status deployment/demo-app -n bizops-demo --context cluster
