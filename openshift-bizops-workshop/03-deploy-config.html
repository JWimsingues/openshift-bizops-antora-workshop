OpenShift BizOps Operations Workshop

Change how the demo app rolls out, practice an image rollback, wire ConfigMap and Secret values into the Deployment, and take a brief look at multitenancy with a second namespace and ResourceQuota. Builds on Session 2.

Prerequisites

  • Completed Session 2

  • demo-app healthy with at least 2 replicas

  • Context cluster available

How It Works

  • RollingUpdate replaces pods gradually so some replicas stay available.

  • Recreate terminates all pods before creating new ones (brief downtime).

  • ConfigMaps hold non-secret settings; Secrets hold sensitive values. Both can be injected as environment variables.

  • Namespaces plus quotas are a lightweight multitenancy boundary (this session does not deep-dive RBAC).

Steps to Apply

1. Compare RollingUpdate and Recreate

~30 seconds for Recreate (pods replaced); RollingUpdate with the same pod template returns almost immediately

What: Apply ConfigMap and Secret, switch the Deployment to Recreate, observe the rollout, then restore RollingUpdate.

Why: BizOps must know when a full cutover is acceptable versus when a rolling update is required for availability.

oc apply -f 03-deploy-config/configmap.yaml --context cluster
oc apply -f 03-deploy-config/secret.yaml --context cluster
oc apply -f 03-deploy-config/deployment-recreate.yaml --context cluster
oc rollout status deployment/demo-app -n bizops-demo --context cluster
oc get deployment demo-app -n bizops-demo -o jsonpath='{.spec.strategy.type}{"\n"}' --context cluster
oc apply -f 03-deploy-config/deployment-rolling.yaml --context cluster
oc rollout status deployment/demo-app -n bizops-demo --context cluster
oc get deployment demo-app -n bizops-demo -o jsonpath='{.spec.strategy.type}{"\n"}' --context cluster
Verify: Strategy is RollingUpdate again 
oc get deployment demo-app -n bizops-demo -o jsonpath='strategy={.spec.strategy.type}{"\n"}' --context cluster
strategy=RollingUpdate

2. Roll back a bad image change

~1 minute (about 60s waiting on the bad image, then undo completes in a few seconds)

What: Point the Deployment at a non-existent tag, observe the bad revision, then roll back.

Why: Rollbacks are the fastest recovery when a new image never becomes Ready.

oc set image deployment/demo-app httpd=registry.access.redhat.com/ubi9/httpd-24:does-not-exist -n bizops-demo --context cluster
oc rollout status deployment/demo-app -n bizops-demo --timeout=60s --context cluster || true
oc get pods -n bizops-demo -l app=demo-app --context cluster
oc rollout undo deployment/demo-app -n bizops-demo --context cluster
oc rollout status deployment/demo-app -n bizops-demo --context cluster
Verify: Pods are Ready again on a valid image 
oc get pods -n bizops-demo -l app=demo-app --context cluster
oc get deployment demo-app -n bizops-demo -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}' --context cluster
NAME                        READY   STATUS    RESTARTS   AGE
demo-app-...                1/1     Running   0          30s
demo-app-...                1/1     Running   0          30s
registry.access.redhat.com/ubi9/httpd-24:latest

3. Review and manage sensitive configuration

What: Confirm Secret and ConfigMap exist and are referenced by the Deployment env vars.

Why: Mis-mounted secrets and config are a common cause of start failures; BizOps must validate both objects and references.

oc get configmap demo-app-config -n bizops-demo -o yaml --context cluster
oc get secret demo-app-secret -n bizops-demo -o jsonpath='{.type}{" keys="}{.data}{"\n"}' --context cluster
oc set env deployment/demo-app --list -n bizops-demo --context cluster
Do not print Secret values in shared terminals or chat logs. Use key existence checks, not oc get secret -o yaml with decoded data in recordings.
Verify: Deployment lists APP_MESSAGE and APP_TOKEN from ConfigMap/Secret 
oc set env deployment/demo-app --list -n bizops-demo --context cluster
# deployments/demo-app, container httpd
APP_MESSAGE from configmap demo-app-config / key: message
APP_TOKEN from secret demo-app-secret / key: token

4. Multitenancy settings (brief)

What: Create a second namespace with a ResourceQuota that caps pods, CPU, and memory.

Why: Soft multitenancy on OpenShift often starts with namespaces and quotas so one team cannot consume the whole cluster. RBAC depth is out of scope for this hour.

oc apply -f 03-deploy-config/tenant-namespace.yaml --context cluster
oc apply -f 03-deploy-config/resourcequota.yaml --context cluster
oc get resourcequota -n bizops-tenant-a --context cluster
oc describe resourcequota team-a-quota -n bizops-tenant-a --context cluster
Verify: Hard limits show pods=10 and CPU/memory caps 
oc get resourcequota team-a-quota -n bizops-tenant-a -o yaml --context cluster | sed -n '/hard:/,/used:/p'
  hard:
    limits.cpu: "2"
    limits.memory: 2Gi
    pods: "10"
    requests.cpu: "1"
    requests.memory: 1Gi

Reset

Restore the rolling baseline Deployment, remove workshop config objects, and delete the tenant namespace. Order matters: remove dependent Deployment env refs by re-applying baseline before deleting Secret/ConfigMap; delete tenant namespace last (it cascades the quota).

oc apply -f 00-baseline/deployment.yaml --context cluster
oc rollout status deployment/demo-app -n bizops-demo --context cluster
oc delete -f 03-deploy-config/secret.yaml --ignore-not-found --context cluster
oc delete -f 03-deploy-config/configmap.yaml --ignore-not-found --context cluster
oc delete -f 03-deploy-config/resourcequota.yaml --ignore-not-found --context cluster
oc delete -f 03-deploy-config/tenant-namespace.yaml --ignore-not-found --wait --context cluster
