OpenShift BizOps Operations Workshop

Prepare a single empty OpenShift cluster with cluster-admin access, create your personal myenv.sh, authenticate with a stable oc context named cluster, clone this repository, and deploy the baseline demo application used in every later session.

Prerequisites

  • OpenShift Container Platform 4.16+ (self-managed or managed such as ROSA; empty app namespaces are fine)

  • oc CLI matching your cluster version

  • git, curl, and envsubst (from gettext)

  • Cluster-admin credentials (username/password or token) provided by your instructor

  • Network access from your workstation to the cluster API and application router

On ROSA and other managed OpenShift services the API URL often uses port 443 (not 6443), and oc get nodes may show worker nodes only. Use the API and console URLs your instructor provides.

Option A - Empty Cluster (Primary Path)

Use this path when the cluster has only the OpenShift platform installed and you have cluster-admin credentials.

1. Create myenv.sh and export workshop variables

What: Create a personal, gitignored file that holds API URL, credentials, and workshop variables.

Why: Credentials must not live in the repository; sourcing one file makes every later command use a stable context name.

Create myenv.sh in the repository root (do not commit it):

cat > myenv.sh <<'EOF'
# Console URL (for quick reference - not used by scripts)
# Console: https://console-openshift-console.apps.<cluster-domain>;

# ── Workshop variables ───────────────────────────────────────────────────
# Self-managed OCP often uses :6443. ROSA / managed OpenShift often uses :443.
export OCP_API_URL="https://api.<cluster-domain>:443"
export GIT_REPO_URL="https://github.com/JWimsingues/openshift-bizops-antora-workshop.git"
export DEMO_NAMESPACE="bizops-demo"

# ── Context cleanup (idempotent) ─────────────────────────────────────────
oc config delete-context cluster 2>/dev/null

# ── Login + rename context ───────────────────────────────────────────────
# Prefer a token if your environment requires it:
# oc login "$OCP_API_URL" --token="<token>"
oc login "$OCP_API_URL" --username <username> --password '<password>'
oc config rename-context "$(oc config current-context)" cluster
EOF

Replace <cluster-domain>, and <username> / <password> (or use --token). Match the API port to your environment (443 for many ROSA clusters, 6443 for many self-managed clusters).

GIT_REPO_URL

DEMO_NAMESPACE

Labs

2. Authenticate and set the cluster context

What: Source myenv.sh so oc logs in and renames the current context to cluster.

Why: Every workshop command uses --context cluster for predictable, shareable instructions.

source myenv.sh
Verify: Context exists and you can query the API 
oc whoami --context cluster
oc get nodes --context cluster
system:admin
NAME                          STATUS   ROLES                  AGE   VERSION
ip-10-0-1-10.example.com      Ready    control-plane,master   3d    v1.29.x
ip-10-0-1-11.example.com      Ready    worker                 3d    v1.29.x
On managed OpenShift you may authenticate as a user with cluster-admin rather than kubeadmin. The context rename pattern is the same.

3. Clone the workshop repository

What: Clone the course repository (or cd into it if you already have a local copy).

Why: YAML manifests and AsciiDoc live side by side; labs apply files from the repo root.

git clone "$GIT_REPO_URL"
cd openshift-bizops-antora-workshop
If you already cloned the repo and created myenv.sh inside it, skip the clone and keep working from that directory.
Verify: Baseline manifests are present 
ls 00-baseline/
deployment.yaml
namespace.yaml
route.yaml
service.yaml

4. Deploy the baseline demo application

~1 minute (image pull ~5-10s when cold; pods Ready in ~30-45s when the image is cached)

What: Apply the namespace, HTML ConfigMap, Deployment, Service, and Route under 00-baseline/.

Why: Later sessions inspect and operate on this same application instead of starting from an empty namespace each time.

Files in 00-baseline/ are ordered so the namespace and ConfigMap are created before the Deployment. 
oc apply -f 00-baseline/ --context cluster
oc rollout status deployment/demo-app -n bizops-demo --context cluster
Verify: Pods are Ready and the Route has a host 
oc get pods,svc,route -n bizops-demo --context cluster
NAME                            READY   STATUS    RESTARTS   AGE

Option B - Quick Re-login

Use this when the baseline app is already deployed and you only need to restore the cluster context on a new terminal.

source myenv.sh
oc get deployment demo-app -n bizops-demo --context cluster

What You Have Now

  • Authenticated oc context named cluster

  • Cloned workshop repository

  • Running demo app in bizops-demo with Service and Route

Continue with Session 1: Architecture and Access.

Reset

Removes the baseline application and namespace. Run this only if you want to tear down setup before re-running Option A. Order: Route and Service first is optional; deleting the namespace removes all namespaced resources.

oc delete -f 00-baseline/ --ignore-not-found --context cluster
oc delete namespace bizops-demo --ignore-not-found --wait --context cluster
